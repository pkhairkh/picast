# BCM2711 SoC Deep Dive

The BCM2711 is the system-on-chip at the heart of the Raspberry Pi 4 Model B. Understanding its media capabilities — particularly the H.264 hardware decoder, the HEVC decoder block, the Hardware Video Scaler (HVS), and the V3D GPU — is essential for building PiCast's playback and display subsystems. This document provides a hardware-level reference for each of these blocks, their interconnections, their constraints, and the software APIs through which PiCast accesses them.

The BCM2711 integrates four Cortex-A72 CPU cores, a VideoCore VI (V3D) GPU, dedicated H.264 and HEVC hardware decoder blocks, and a Hardware Video Scaler (HVS) on a single die connected via the System Control Bus (SCB) interconnect. The H.264 and HEVC decoder blocks are architecturally and electrically distinct — they use different drivers, different V4L2 API models, and produce different output formats. The HVS is a fixed-function compositing engine that reads from DMA-BUF-backed framebuffers and outputs to the HDMI transmitter. The V3D GPU is a 3D graphics processor that PiCast uses exclusively for OSD overlay rendering.

## H.264 Decoder (V4L2 M2M)

The primary decode path for PiCast uses the BCM2711's dedicated H.264 decoder, exposed through the `bcm2835-codec` kernel driver as V4L2 memory-to-memory (M2M) devices. This is the proven, production-quality decode path that underpins PiCast's entire zero-copy video pipeline.

### Capabilities

| Parameter | Value |
|-----------|-------|
| Driver | bcm2835-codec (mainline Linux) |
| API Model | V4L2 stateful M2M |
| Profiles | Baseline, Main, High |
| Max Level | 4.2 |
| Max Resolution | 1920×1080 @ 60fps |
| Pixel Formats (OUTPUT) | V4L2_PIX_FMT_H264 |
| Pixel Formats (CAPTURE) | NV12 (two-plane 4:2:0) |
| Buffer Export | DMA-BUF fd (zero-copy compatible) |
| Max Bitrate | ~50 Mbps |
| GStreamer Element | v4l2h264dec (io-mode=dmabuf) |

### V4L2 Device Paths

| Device | Path | Purpose |
|--------|------|---------|
| Video decoder | `/dev/video10` | Compressed H.264 stream input (OUTPUT queue) and decompressed NV12 output (CAPTURE queue) — M2M single-device model |
| Video encoder | `/dev/video11` | H.264 encoding (not used by PiCast) |
| ISP | `/dev/video12` | Image Sensor Processor — color space conversion, format transformation (used for SAND→NV12 in future HEVC support) |
| Deinterlace | `/dev/video20` | Video deinterlacing (not used by PiCast) |

### Stateful V4L2 API

The H.264 decoder uses the **stateful** V4L2 API model. In this model, the application feeds raw compressed H.264 NALUs into the OUTPUT queue, and the driver internally manages all decoder state including sequence parameter sets (SPS), picture parameter sets (PPS), decoded picture buffer (DPB) management, reference frame lists, and B-frame reordering. The application does not need to parse slice headers, manage reference pictures, or handle B-frame reordering — the hardware and driver handle all of this autonomously.

This contrasts with the stateless API used by the HEVC decoder, where the application must parse the bitstream and provide per-slice control parameters to the hardware. The stateful model is simpler to implement and is the primary reason the H.264 path is preferred for PiCast v1.

### NV12 Output Format

The decoder's CAPTURE queue outputs decoded frames in **NV12 format** (4:2:0 chroma subsampling, two-plane: Y plane followed by interleaved UV plane) as **DMA-BUF file descriptors**. NV12 is the native scanout format of the HVS — the Hardware Video Scaler can read NV12 buffers directly from DMA-BUF without any format conversion. This is the hardware foundation of PiCast's zero-copy pipeline: the decoder writes NV12 pixels into a DMA-BUF, and the HVS reads those same pixels from the same DMA-BUF during HDMI scanout. No copy, no conversion, no CPU involvement.

### Key ioctls

| ioctl | Purpose |
|-------|---------|
| `VIDIOC_REQBUFS` | Request buffer allocation (DMA-BUF mode for zero-copy) |
| `VIDIOC_QBUF` | Queue a buffer for processing |
| `VIDIOC_DQBUF` | Dequeue a completed buffer |
| `VIDIOC_STREAMON` | Start streaming on a queue |
| `VIDIOC_STREAMOFF` | Stop streaming on a queue |
| `VIDIOC_S_FMT` | Set format (OUTPUT: H.264, CAPTURE: NV12) |
| `VIDIOC_G_FMT` | Get current format |
| `VIDIOC_ENUM_FMT` | Enumerate supported pixel formats |
| `VIDIOC_QUERYCAP` | Query device capabilities |
| `VIDIOC_G_SELECTION` | Get crop/compose rectangles |
| `VIDIOC_EXPBUF` | Export buffer as DMA-BUF file descriptor |
| `VIDIOC_SUBSCRIBE_EVENT` | Subscribe to source change events for ABR resolution changes |

### Resolution Change Handling

When the H.264 stream changes resolution (e.g., during an ABR quality switch), the decoder emits a `V4L2_EVENT_SOURCE_CHANGE` event. PiCast must handle this by: (1) stopping the CAPTURE queue, (2) re-negotiating the CAPTURE format via `VIDIOC_G_FMT` to get the new resolution, (3) reallocating CAPTURE buffers, and (4) restarting the CAPTURE queue. GStreamer's `v4l2h264dec` element handles this automatically.

## HEVC/H.265 Decoder (Stateless V4L2 Request)

The BCM2711 also contains a separate HEVC/H.265 decoder hardware block, which is architecturally and electrically distinct from the H.264 decoder. This decoder supports HEVC Main Profile, Level 5.0, up to 4Kp60 at 8-bit depth. However, PiCast v1 does not use this decoder due to a critical output format incompatibility with the HVS.

### Capabilities

| Parameter | Value |
|-----------|-------|
| Driver | rpivid (downstream Raspberry Pi kernel) / rpi-hevc-dec (upstream WIP, patch v5 as of Feb 2026) |
| API Model | V4L2 stateless Request API |
| Profiles | Main, Main 10 |
| Max Level | 5.0 |
| Max Resolution | 3840×2160 @ 60fps (8-bit) |
| Pixel Formats (OUTPUT) | HEVC bitstream + per-slice controls |
| Pixel Formats (CAPTURE) | NC12/NC30 (SAND column format) |
| Zero-Copy to Display | **No** — SAND format incompatible with HVS |
| GStreamer Element | v4l2slh265dec (stateless) |

### The SAND Format Problem

The critical problem with the HEVC decoder is its output format. The HEVC hardware block outputs decoded frames in **SAND column format** (also called "tiled" or "handed" format, with V4L2 pixel format codes NC12 for 8-bit and NC30 for 10-bit). SAND format stores pixel data in columns of 128-byte width, which is efficient for the decoder's internal memory access patterns but is completely incompatible with the HVS. The Hardware Video Scaler can only scan out linear NV12/P030 formats — it has no SAND deinterleaver. This means HEVC decode output **cannot be displayed without a format conversion step**, which fundamentally breaks the zero-copy pipeline.

### Conversion Options

| Conversion Method | Performance | Zero-Copy | Status |
|---|---|---|---|
| NEON SIMD (ARM) | ~30fps at 4K, ~120fps at 1080p | No (CPU reads + writes) | Available now |
| bcm2835-ISP (hardware) | ~60fps at 4K | No (separate DMA-BUF allocation) | Available now |
| V3D compute shader | Unknown (unproven) | Potentially near-zero-copy | Research phase |
| Kernel driver conversion | Depends on implementation | No (extra buffer) | Not implemented |

Any conversion step requires writing from one DMA-BUF (SAND) into another DMA-BUF (NV12), consuming memory bandwidth and CPU/GPU time. For PiCast v1, this is entirely avoided by forcing H.264 format selection through yt-dlp. HEVC support is deferred to v2.

### H.264 vs HEVC Comparison

| Parameter | H.264 Decoder | HEVC Decoder |
|---|---|---|
| Hardware block | Separate dedicated block | Separate dedicated block |
| Driver | bcm2835-codec (mainline) | rpivid (downstream), rpi-hevc-dec (upstream WIP) |
| V4L2 API | Stateful M2M | Stateless Request |
| Max resolution | 1080p60 | 4Kp60 (8-bit) |
| Output format | NV12 (linear) | NC12/NC30 (SAND column) |
| HVS-compatible | Yes (direct scanout) | No (requires conversion) |
| Zero-copy to display | Yes | No |
| PiCast v1 support | **Primary path** | Not supported |

## HVS (Hardware Video Scaler)

The Hardware Video Scaler (HVS) is the BCM2711's dedicated display compositor, operating entirely independently of the V3D GPU. It is a fixed-function hardware block that reads pixel data from DMA-BUF-backed framebuffers, performs scaling, colorspace conversion, and alpha blending across multiple input planes, and outputs the composited result to the HDMI transmitter. The HVS runs continuously, scanning out a full frame to HDMI every 16.67ms at 60Hz, regardless of whether the application is actively rendering.

### HVS Channels and Planes

PiCast uses the HVS in its most efficient configuration: two input planes on Channel 0. **Plane 0** carries the decoded video frame (NV12 DMA-BUF from the V4L2 decoder), and **Plane 1** carries the OSD overlay (ARGB8888 GBM buffer from the V3D GPU). The HVS performs hardware alpha-blending of these two planes during each scanout cycle.

| Channel | Planes | Use in PiCast |
|---------|--------|---------------|
| 0 | 1 (primary, ZPOS 0) + 1 (overlay, ZPOS 1) | Video + OSD on HDMI-A-1 |
| 1 | 1 (primary) | Second HDMI output (unused on Pi 4) |
| 2 | 1 (primary) | Reserved (DSI display, unused) |

### Supported Input Formats

| Format | FourCC | Bits per Pixel | Layout | HVS Scanout | PiCast Usage |
|--------|--------|---------------|--------|-------------|-------------|
| NV12 | DRM_FORMAT_NV12 | 12 | Y plane + interleaved UV | Yes | Video decode output (Plane 0) |
| ARGB8888 | DRM_FORMAT_ARGB8888 | 32 | Packed ARGB | Yes | OSD overlay (Plane 1) |
| XRGB8888 | DRM_FORMAT_XRGB8888 | 32 | Packed RGB (no alpha) | Yes | Alternative OSD format |
| SAND (NC12) | — | 12 | Column-tiled Y+UV | **No** | HEVC output (incompatible) |
| P030 | DRM_FORMAT_P030 | 24 | 10-bit Y+UV | Yes (with format flag) | Future 10-bit HEVC |

### Plane Priority and Z-Ordering

The HVS composites planes from lowest ZPOS to highest. Lower-numbered planes are composited first and appear "behind" higher-numbered planes. PiCast uses:
- **ZPOS 0 (Plane 31, Primary)**: Video framebuffer — the bottom layer
- **ZPOS 1 (Plane 32, Overlay)**: OSD overlay — composited on top of video

If the Z-order is reversed (OSD on ZPOS 0, video on ZPOS 1), the OSD would be hidden behind the video and invisible. The ZPOS assignment must match this convention.

## V3D GPU (VideoCore VI)

The V3D GPU in the BCM2711 is a VideoCore VI part supporting OpenGL ES 3.1 and delivering approximately 24 GFLOPS of compute performance. It is critical to understand that the V3D is a **3D graphics processor**, not a video decoder. It cannot decode H.264 or HEVC bitstreams — that is the job of the dedicated decoder blocks described above.

### Capabilities

| Parameter | Value |
|-----------|-------|
| OpenGL ES | 3.1 |
| Vulkan | Not supported on Pi 4 (requires Pi 5) |
| Max Texture Size | 4096×4096 |
| Shader Cores | 2 (QPU) |
| Clock | 500 MHz |
| Fill Rate | ~1 Gpixel/s |

### Role in PiCast: OSD Rendering

In PiCast, the V3D GPU serves a single purpose: **rendering the OSD overlay** on DRM Plane 1. This includes subtitle text rendered by Pango/Cairo via an EGL/GBM surface, and any transient status indicators (buffering animation, error messages, volume level). The GPU renders these elements into an ARGB8888 GBM buffer, which the HVS alpha-blends on top of the video plane during scanout.

The rendering pipeline is:

```
1. Create GBM device from DRM FD
2. Create EGL display on GBM device
3. Create EGL context (OpenGL ES 3.1)
4. Create GBM buffer (SCANOUT | RENDERING) for rendering target
5. Create EGL surface from GBM buffer's DMA-BUF
6. Render text with glyph atlas texture + simple textured quad shader
7. glFlush() + eglSwapBuffers()
8. Export GBM buffer as DRM framebuffer
9. Assign to overlay plane (ZPOS 1) via atomic commit
```

### V3D Device Nodes

| Device | Path | Purpose |
|--------|------|---------|
| Render node | `/dev/dri/renderD128` | V3D GPU — no auth needed, used for off-screen rendering |
| V3D device | `/dev/v3d` | Direct V3D access (not used by PiCast) |

### Future: Compute Shader for SAND→NV12

The V3D's compute capabilities (OpenGL ES 3.1 compute shaders) represent a potential future optimization path for the SAND→NV12 conversion problem described in the HEVC section. A compute shader could transform SAND-column data into linear NV12 directly on the GPU, writing the output to a DMA-BUF that the HVS could then scan out. This would be "near-zero-copy" — the data would move from the HEVC decoder's DMA-BUF to the GPU for transformation and then to a new DMA-BUF for display, but the CPU would not be involved and the data would never enter main memory. However, this approach is unproven and deferred to PiCast v2.

### CMA (Contiguous Memory Allocator)

The BCM2711 allocates contiguous memory for video buffers from CMA. The default CMA size is 256 MB, which may be insufficient for multiple 1080p decode buffers. Increase it via the kernel command line:

```
# /boot/cmdline.txt
cma=384M
```

### DMA-BUF Export/Import Flow

```
V4L2 CAPTURE queue
    │
    ▼ (VIDIOC_EXPBUF → DMA-BUF FD)
    │
    ├──▶ GStreamer v4l2h264dec → kmssink (drmPrimeFDToHandle → ADDFB2 → atomic commit)
    │
    └──▶ picast-display overlay plane (GBM buffer → DRM FB → atomic commit)
```

The DMA-BUF framework allows zero-copy sharing of video frames between the V4L2 decoder, GStreamer, and the DRM/KMS display without copying pixel data through CPU memory. Each DMA-BUF fd is a handle to physically contiguous (or IOMMU-mapped) memory that both the decoder hardware and the HVS can access directly.
