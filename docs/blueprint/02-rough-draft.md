# boGDan Rough Draft

## Approach

This rough draft proposes a concrete solution, an alternative that was considered and rejected, and an identified risk for each of the twelve problems catalogued in `01-problem-catalog.md`. The solutions are grounded in the architecture already ratified in `ARCHITECTURE.md` and `SPECIFICATION.md` — Tor as a non-negotiable security substrate with per-site `IsolateSOCKSAuth` circuit isolation, a zero-copy V4L2→DMA-BUF→DRM/KMS decode pipeline that excludes X11/Wayland/Chromium/Widevine entirely, and a three-protocol surface (HTTP REST, WebSocket, UPnP/DLNA) backed by a single session state machine. Where the catalog identifies a nice-to-have that the current architecture does not yet address (thermal management, multi-room sync, web-UI accessibility), this draft proposes minimal, v1-appropriate solutions and explicitly defers the heavier work to v2. Each risk is paired with a mitigation sketch rather than a full remediation plan; detailed mitigations belong in the next blueprint phase.

## Problems Addressed

### [[P-001]] — Mandatory Tor routing with per-site circuit isolation and DNS-leak defense-in-depth
- **Approach:** All content resolution and media fetching is forced through the local Tor daemon (`127.0.0.1:9050`, `IsolateSOCKSAuth`) using the `socks5h://` scheme so DNS is resolved by the Tor exit relay, never locally. Per-site stream isolation is achieved by constructing the SOCKS5 username as `bogdan-<domain-hash>` (first 8 hex chars of the domain hash), so YouTube, Vimeo, and direct CDN traffic each ride independent circuits. DNS leakage is prevented at three layers: SOCKS5h remote resolution, a local `dnsmasq` configured to refuse all upstream queries, and an iptables OUTPUT chain that DROPs any outbound UDP/53 to non-local addresses. Verification is by `tcpdump` showing only Tor connections leaving the appliance.
- **Alternative considered:** A commercial VPN was rejected because a single VPN provider sees the user's entire traffic graph — Tor's three-relay circuit means no single relay can link the user to the content. The Rust `arti` client was also considered but rejected because, as of its current implementation, it lacks `IsolateSOCKSAuth`, which is the exact primitive boGDan needs for per-site circuit isolation.
- **Risk:** Tor throughput (0.5–5 Mbps) caps playable resolution at a 720p default and makes 1080p unreliable. Mitigation: the ABR controller (§10.3 of the architecture) downshifts to 480p/360p when the `queue2` buffer drops below 10%, and the 50 MB `queue2` buffer absorbs 30–60 s of circuit stalls before playback is interrupted.

### [[P-002]] — DRM-free, display-server-free appliance via direct DRM/KMS scanout
- **Approach:** Eliminate X11, Wayland, Chromium, and the Widevine CDM entirely. Decoded frames flow from `v4l2h264dec` as DMA-BUF file descriptors directly into `kmssink`, which programs DRM plane 0 via atomic modesetting for HDMI scanout — the CPU never touches pixel data. The `bogdand` systemd unit runs as a dedicated `bogdan` user with `NoNewPrivileges`, dropped capabilities, and only the `video`/`render`/`audio`/`debian-tor` group memberships needed for DRM, V4L2, ALSA, and Tor SOCKS access. Resource budget targets < 200 MB RAM during 1080p playback.
- **Alternative considered:** A Wayland compositor (weston/sway) was rejected because it adds ~50–100 MB RAM and a compositor copy hop, which breaks the zero-copy property that keeps CPU utilization near 3%. A headless Chromium kiosk was also considered and rejected as ~300 MB+ RAM plus the entire Blink+V8 stack, which defeats the appliance model and re-introduces the DRM problem boGDan exists to avoid.
- **Risk:** Without a compositor, OSD and subtitle rendering cannot use a normal windowing path. Mitigation: render OSD text onto a secondary DRM plane via the Hardware Video Scaler (HVS), and burn subtitles into the video plane using the experimental V3D GPU compute path (`src/v3d/`) when present; otherwise subtitle support is limited to text overlays on plane 0.

### [[P-003]] — Zero-copy V4L2 stateful H.264 decode pipeline with DMA-BUF export
- **Approach:** Use the BCM2711's stateful V4L2 memory-to-memory H.264 decoder (`v4l2h264dec`) in DMA-BUF export mode, with `parsebin` auto-detecting the container and a `pad-added` callback dynamically building the decode chain. The full video path is `appsrc → queue2 → parsebin → v4l2h264dec → v4l2convert (bcm2835-ISP) → kmssink (DRM plane 0)`, and audio is `parsebin → avdec_aac → audioconvert → vol → alsasink`. Decoded frames leave the decoder as DMA-BUF file descriptors that `kmssink` imports directly into a DRM plane, so the ARM cores are uninvolved in the display data path. Target: 1080p60 at < 50% CPU; the architecture reports ~3% CPU on 1080p60.
- **Alternative considered:** The stateless V4L2 request API (`v4l2slh265dec`) was considered for H.264 but rejected because the stateful M2M API is simpler and well-supported on BCM2711 for H.264; the stateless path is reserved for HEVC. Pure software decode via `avdec_h264` was rejected outright because it caps at ~30 fps at 1080p and causes thermal throttling on the Pi 4.
- **Risk:** The BCM2711 HEVC decoder outputs SAND-format frames that the HVS cannot scan out directly, so HEVC cannot use this zero-copy path in v1. Mitigation: ship H.264-only decode in v1, document HEVC as unsupported, and defer the SAND→NV12 conversion (via V3D compute shader, `src/v3d/` experimental module) to v2 per OD-001.

### [[P-004]] — Unified three-protocol surface backed by one session state machine
- **Approach:** Expose HTTP REST on 8585 (control: `/api/cast`, `/api/stop`, `/api/pause`, `/api/seek`, `/api/status`), WebSocket on 8586 (real-time state broadcasts), and a UPnP/DLNA MediaRenderer on 49152 (AVTransport:1 and RenderingControl:1). Device discovery is via SSDP on 1900 (for DLNA) and mDNS on 5353 (for `bogdan.local`). All three protocol adapters translate their inputs into the same six-state session machine (IDLE → RESOLVING → BUFFERING → PLAYING → PAUSED → ERROR), so a DLNA `SetAVTransportURI` and an HTTP `/api/cast` drive identical downstream behavior.
- **Alternative considered:** HTTP REST only was rejected because DLNA is mandatory for VLC/Plex/Home Assistant interop and WebSocket is required for real-time status without polling. gRPC was considered for the extension↔appliance link but rejected because no DLNA client and no Manifest V3 service worker speaks it natively.
- **Risk:** The DLNA spec is loosely implemented across clients (VLC, MiniDLNA, Plex, BubbleUPnP each interpret AVTransport slightly differently). Mitigation: ship a DLNA conformance test harness in `scripts/`, test against at least two third-party clients per release, and ensure `SetAVTransportURI` accepts the same URL forms (page URL, direct media URL, `.m3u8`/`.mpd` manifests) as `/api/cast`.

### [[P-005]] — Per-site circuit reuse with queue2-backed stall absorption and fast re-resolution
- **Approach:** Reuse a per-site Tor circuit within `MaxCircuitDirtiness` (600 s) to amortize the 5–15 s circuit-build cost across consecutive videos from the same site, while `IsolateSOCKSAuth` guarantees different sites never share a circuit. The 50 MB `queue2` buffer holds 30–60 s of 720p video, absorbing circuit rotations and transient stalls. On an unrecoverable stream failure, the resolver re-extracts the URL through a fresh SOCKS username (appending a session counter to the domain hash) to force a new circuit, and the ABR controller downshifts resolution if the buffer drops below 10%. `ControlPort 0` in torrc — no NEWNYM signaling is needed.
- **Alternative considered:** Tor control-port-driven `NEWNYM` signaling was rejected as unnecessary because `IsolateSOCKSAuth` gives deterministic, per-username isolation without any control-port chatter (which would also expand the attack surface). `arti`'s stream isolation was considered but, as noted in P-001, arti lacks `IsolateSOCKSAuth`.
- **Risk:** A mid-stream circuit failure triggers a 5–30 s yt-dlp re-extraction stall, which can exceed the catalog's 5 s success metric. Mitigation: at session start, prefetch alternate-format URLs (e.g., 480p and 360p variants) so a downshift is a buffer switch rather than a full re-resolution, and keep `queue2` filled above the 10% low threshold so playback continues during re-resolution.

### [[P-006]] — Two-tier resolver with CDN preflight and speed-limit bypass
- **Approach:** Tier 1 invokes `yt-dlp` (1800+ sites) with `--proxy "socks5h://bogdan-<domain-hash>:x@127.0.0.1:9050"` and a `maxResolution` hint; Tier 2 handles direct media URLs (`.mp4`, `.m3u8`, `.mpd`, `.ts`, `.webm`, `.m4s`) without yt-dlp. Before starting the full download, a CDN preflight issues `GET` with `Range: bytes=0-0` (not `HEAD`, which many CDNs answer with 404). If the resolved URL contains a speed-limit parameter (e.g., `sp=380` capping throughput at ~380 kbps), the resolver tries bypass variants (`sp=99999`, `sp=` stripped); if all bypasses return 403, it falls back to the original rate-limited URL. Target: YouTube resolution in < 10 s.
- **Alternative considered:** A `torMode=resolution-only` mode (Tor for yt-dlp, direct fetch for the media stream) is exposed as an opt-in for trusted LANs where the user accepts CDN IP exposure, but the default remains `torMode=full`. Shipping custom per-site extractors was rejected because yt-dlp's community-maintained extractor set is broader and stays current with site changes faster than a small open-source project can.
- **Risk:** yt-dlp extractors break when sites change their HTML/JS, causing resolution failures. Mitigation: bundle yt-dlp, support `sudo yt-dlp -U` for self-update, and fall back to the browser extension's intercepted media URL (P-007) when yt-dlp fails on a site the extension can intercept.

### [[P-007]] — Manifest V3 browser extension with intercept-first, fallback-second modes
- **Approach:** A Manifest V3 extension for Chrome and Firefox operates in two modes selected automatically. Intercept mode uses `declarativeNetRequest` with dynamic rules matching `.m3u8`, `.mpd`, `.mp4`, `.ts`, `.webm`, `.m4s`; a captured media URL is sent directly to `/api/cast`, bypassing yt-dlp. Fallback mode sends the page URL for server-side yt-dlp resolution (3–15 s). The popup shows playback state over the WebSocket channel and offers cast/stop/pause. An opt-in MSE interception feature (content script in `world: "MAIN"` monkey-patching `SourceBuffer.appendBuffer`) handles sites with encrypted or non-standard segment delivery. Configuration (`piAddress`, `torMode`, `maxResolution`, `preferIntercepted`, `autoCast`) is synced via `chrome.storage.sync`.
- **Alternative considered:** Manifest V2 was rejected as deprecated and removed from Chrome. A native Electron app was rejected as a ~100 MB install that defeats the lightweight-appliance goal. Pure page-URL submission (no intercept) was rejected as too slow per cast and as failing on sites yt-dlp doesn't support.
- **Risk:** `declarativeNetRequest` imposes a dynamic-rule quota (Chrome caps static+dynamic rules) and MV3 service workers can be suspended by the browser. Mitigation: use a small, high-recall pattern rule set plus URL inspection in the popup rather than thousands of specific rules; persist pending cast state in `chrome.storage` so a suspended service worker resumes the cast on wake. MSE interception can break on DRM-encrypted segments or CSP-protected pages — it remains opt-in and off by default, with fallback mode as the reliable path.

### [[P-008]] — Three-path headless install with mDNS-discoverable web configuration UI
- **Approach:** Three install paths: (1) `curl -sSL https://raw.githubusercontent.com/pkhairkh/picast/main/scripts/setup.sh | sudo bash` on Raspberry Pi OS Lite 64-bit Bookworm, then reboot; (2) a pre-built `.deb` installed via `dpkg -i`; (3) a pre-flashed SD card image from GitHub Releases. The `bogdan.service` systemd unit starts after `tor.service` and auto-restarts on failure with a 30 s watchdog. A web UI at `http://bogdan.local` (mDNS) exposes Tor bridge configuration, network settings, and media-source defaults — no SSH required for normal operation.
- **Alternative considered:** A Docker container was rejected because Docker on Pi adds overhead and complicates bare-metal DRM/V4L2 device access that the appliance model depends on. An Ansible playbook was rejected as too heavy for end users. A serial-console setup wizard was rejected because most users lack serial access to the Pi.
- **Risk:** `curl | bash` is a supply-chain concern, and `bogdan.local` mDNS resolution is unreliable on some networks (notably corporate Wi-Fi that blocks mDNS). Mitigation: pin the installer to a specific release tag, ship a SHA256 checksum the user can verify, and publish the `.deb` and SD image as signed GitHub release artifacts; on first boot, print the Pi's DHCP-assigned IP to the TV via the OSD plane so users on mDNS-hostile networks can reach the web UI at `http://<ip>:8585` directly.

### [[P-009]] — Native DLNA MediaRenderer with shared session backend
- **Approach:** boGDan advertises itself as a UPnP `MediaRenderer` (device type `urn:schemas-upnp-org:device:MediaRenderer:1`) on port 49152, implementing `AVTransport:1` (`SetAVTransportURI`, `Play`, `Pause`, `Stop`, `Seek`, `GetPositionInfo`) and `RenderingControl:1` (`SetVolume`, `GetVolume`). SSDP M-SEARCH on 1900 is answered so VLC, MiniDLNA, Plex, and BubbleUPnP discover the appliance. The DLNA layer translates `SetAVTransportURI` into the same internal call as `/api/cast`, so the session state machine, resolver, and pipeline are shared across all three protocol surfaces.
- **Alternative considered:** A DLNA MediaServer role was rejected because boGDan is a receiver, not a media library. A native Rust DLNA stack was considered as the cleanest long-term path, but for v1 `gmediarender` is acceptable as a battle-tested stopgap for protocol handling. Native Rust DLNA is deferred to v2.
- **Risk:** `gmediarender` holds the DRM master and can conflict with `bogdand`'s `kmssink` on restart (the catalog's known issue: "DRM master busy on restart"). Mitigation: coordinate DRM-master acquisition via a lock file or systemd `ExecStartPost`/`ExecStopPost` ordering, and configure `gmediarender` to handle only DLNA protocol translation — feeding its resolved URL back into `bogdand`'s pipeline rather than rendering independently — so only `bogdand` ever touches the DRM plane.

### [[P-010]] — Thermal monitoring with staged ABR downshift and cool-down pause
- **Approach:** Poll `/sys/class/thermal/thermal_zone0/temp` every 5 s. Below 75 °C: no action. 75–80 °C: log a warning. Above 80 °C: trigger an ABR downshift (re-resolve at 480p/360p via yt-dlp) and reduce the `queue2` prefetch rate. Above 85 °C: pause decode and display a "cooling down" OSD message until temperature drops below 75 °C. The systemd watchdog also observes temperature. Target: CPU temperature stays below 75 °C during 1080p playback.
- **Alternative considered:** CPU frequency scaling (`cpufreq ondemand`) is already enabled by Raspberry Pi OS but is insufficient alone because the thermal bottleneck on the Pi 4 during video playback is the V4L2 decoder block and the HVS, not the ARM cores. Active fan control via PWM was considered but is out of scope for software — it is documented as a hardware recommendation in the user guide (a small 5 V fan + heatsink).
- **Risk:** An ABR downshift during a thermal event triggers a 5–30 s yt-dlp re-resolution stall, which can itself prolong the high-temperature state. Mitigation: pre-resolve lower-bitrate format URLs at session start so a downshift is a buffer switch, not a re-resolution. Because this is a nice-to-have, v1 can ship with monitoring + warning only and defer automatic downshift to v1.1.

### [[P-011]] — LAN leader-elected clock sync with scheduled playback start (v2)
- **Approach:** Appliances on the same LAN elect a leader (lowest mDNS hostname wins, with a tie-break on MAC address). Each appliance timestamps its GStreamer render clock against the leader's wall clock via a simple UDP heartbeat + JSON status on a multicast group. Playback start is scheduled at a future wall-clock time (e.g., T+2 s) so all appliances begin simultaneously. Ongoing drift is corrected by micro-adjusting the pipeline rate or dropping/repeating a frame at a buffer boundary. Target: < 100 ms audio offset between two appliances.
- **Alternative considered:** IEEE 1588 PTP was rejected because the Pi 4's Ethernet MAC lacks hardware PTP timestamping, and software PTP cannot reliably hit 100 ms. A single master that streams decoded frames to slaves was rejected because it breaks the zero-copy appliance model and adds per-slave bandwidth. SMPTE LTC over audio was considered and rejected as overkill for a home multi-room setup.
- **Risk:** Because each appliance fetches media independently through its own Tor circuit, arrival times can diverge significantly. Mitigation: pre-buffer to a common wall-clock target with a long (e.g., 60 s) lead time so drift is bounded by buffer depth rather than network jitter. This is explicitly a v2 feature; v1 documents the limitation clearly so users with multiple appliances are not surprised by desync.

### [[P-012]] — Accessible web UI with semantic HTML, ARIA, keyboard nav, and high-contrast mode
- **Approach:** The web configuration UI is built with semantic HTML (`<button>`, `<nav>`, `<main>`, `<form>`, `<fieldset>`/`<legend>`), ARIA labels on every interactive element, full keyboard navigation (logical tab order, Enter/Space activation, Esc to close modals), and a high-contrast toggle backed by CSS custom properties and persisted in `localStorage`. A skip-to-content link is the first focusable element. The status region uses `aria-live="polite"` so state transitions are announced without spamming transient buffer percentages. The UI is evaluated with WAVE and tested with NVDA and VoiceOver as part of CI.
- **Alternative considered:** A separate text-only/terminal UI was rejected because it duplicates maintenance and most users want the visual configuration surface. A CLI-only config tool was rejected because it excludes the non-technical users that the headless-appliance goal (P-008) is designed to serve. Relying solely on the OS-level high-contrast media query was kept as an enhancement layered on top of the in-app toggle, not as a replacement, because not all users configure their OS for high contrast.
- **Risk:** WebSocket-driven status updates can confuse screen readers if the live region is not marked correctly, and the DLNA/Tor configuration forms have many fields that can overwhelm tab navigation. Mitigation: mark only state transitions in `aria-live="polite"`, group form fields with `<fieldset>`/`<legend>`, bind validation errors via `aria-describedby`, and gate releases on a clean WAVE evaluation in CI.
